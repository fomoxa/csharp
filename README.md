# Cyclone C#

The Cyclone runtime for .NET, written from the specification: framing, the schema
handshake, heartbeat, and a non-blocking TCP/UDP tick loop.

No NuGet dependency. No threads. No `async`. `netstandard2.1`, so the same
assembly runs on .NET 6/7/8/9 and inside Unity 2021+ under IL2CPP.

```sh
dotnet build Cyclone.Net.sln
dotnet run --project tests/Cyclone.Net.Tests   # 69 checks, no test framework needed
```

## What this is, and what it answers to

The [protocol specification](https://github.com/cyclone-protocol/protocol-specification)
is the authority here, and nothing else is:

| Document | What it fixes |
|---|---|
| RFC-0001 | What Cyclone is, and the five design decisions behind it |
| RFC-0002 | The byte layout: primitives, string, bytes, model, array, enum, version differences |
| RFC-0003 | Conformance: the test vectors an implementation must pass, all of them |
| [Implementation guide](https://github.com/cyclone-protocol/protocol-implementation-guide) | The layer above: framing, handshake, heartbeat, the transport contract |

Where this library and any other Cyclone SDK disagree, the RFCs decide, and both
sides agreeing with each other proves nothing.

Three layers, and this library is one of them:

```
  your application
        |
  codec         RFC-0002 - Model <-> bytes                  generated by cyclonec,
                                                            NOT in this repository
        |
  runtime       implementation guide - frames, handshake,   src/Cyclone.Net/Framing,
  (this repo)   heartbeat, tick loop, events                Session.cs, CycloneConnection.cs,
                                                            CycloneServer.cs
        |
  transport     TCP or UDP, or one you write yourself       src/Cyclone.Net/Transports
```

A message payload is opaque here, from the socket all the way up to the event
handed to your application. Nothing in this repository reads a byte of it.

## Quick start

### Client

```csharp
using Cyclone.Net;
using Cyclone.Net.Transports;

var transport = TcpTransport.Connect(new IPEndPoint(IPAddress.Loopback, 7777));
using var connection = CycloneConnection.Connect(transport, MySchema.Build(), new SessionConfig());

while (!connection.IsClosed)
{
    foreach (var raised in connection.Tick(MonotonicClock.Now))
    {
        switch (raised.Kind)
        {
            case CycloneEventKind.Ready:
                break;

            case CycloneEventKind.Message:
                Handle(raised.MessageId, raised.Payload.Span);
                break;

            case CycloneEventKind.HandshakeFailed:
            case CycloneEventKind.Disconnected:
                return;
        }
    }

    if (connection.IsReady)
    {
        connection.Send(MySchema.PositionMessageId, payload);
    }

    Thread.Sleep(16);
}
```

`Send` before `Ready` is refused; no application byte reaches the wire before both
ends have agreed they read bytes the same way.

### Server

```csharp
var listener = new TcpListenerTransport(new IPEndPoint(IPAddress.Loopback, 7777));
using var server = new CycloneServer(listener, MySchema.Build(), new SessionConfig());

while (true)
{
    foreach (var raised in server.Tick(MonotonicClock.Now))
    {
        if (raised.Kind == CycloneEventKind.Message)
        {
            server.Send(raised.PeerId, raised.MessageId, raised.Payload.Span);
        }
    }

    Thread.Sleep(16);
}
```

`examples/EchoServer` and `examples/EchoClient` are two runnable processes doing
exactly this. Start the server first:

```sh
dotnet run --project examples/EchoServer          # add "7777 udp" for UDP
dotnet run --project examples/EchoClient
```

### UDP

Same code, one line different, on both ends:

```csharp
var transport = UdpTransport.Connect(new IPEndPoint(IPAddress.Loopback, 7777));
var listener  = new UdpServerTransport(new IPEndPoint(IPAddress.Loopback, 7777));
```

Everything above the transport is untouched: the same events, the same tick, the
same heartbeat. What changes is what UDP itself does not promise - packets may be
lost, reordered, or duplicated, and this library hands them up **in the order it
received them**, correcting nothing. Heartbeat and dead-peer detection still work,
because they run on a clock rather than on sequence numbers.

## The schema you hand it

The runtime never computes a fingerprint. Your application supplies, per message,
the triple *(id, field count, prefix fingerprint chain)*, and the runtime only
compares:

```csharp
public static Schema Build() =>
    new Schema(
        Handshake.CycloneSchemaFingerprint,
        new[]
        {
            new MessageSchema(
                Handshake.PlayerEdgeMessageId,
                Handshake.PlayerEdgeFingerprint,
                Handshake.PlayerEdgePrefixes),
        });
```

Those constants are what `cyclonec` emits into `Handshake.cs`. The chain is
never sent whole: a peer sends its field count and its last entry, and the
comparison happens at the smaller of the two counts - RFC-0002 §9.1's prefix
test, written out as bytes.

Two peers running **different** schemas still connect, as long as every message
both of them declare agrees on the fields both of them carry. A field appended at
the end of a message, or dropped from the end, is a valid version difference and
RFC-0003 §8.6 vectors V-001/V-002 say it MUST NOT be rejected. Only a field that
differs at an index both ends carry closes the session.

## Timekeeping is a parameter, not a clock read

`Tick(TimeSpan now)` takes the instant from outside. Nothing inside this library
reads a clock of its own, which is what makes a whole expiry cycle testable
without waiting for it - every timeout test in this repository runs in
microseconds.

`MonotonicClock.Now` is offered for callers who want a default. It is backed by
`Stopwatch`, never by wall-clock time: a system time sync stepping backwards must
not expire a running handshake or kill a healthy peer.

Defaults, all reconfigurable through `SessionConfig`:

| Setting | Default | Meaning |
|---|---|---|
| `HandshakeTimeout` | 5 s | Client: the deadline for the whole handshake. Server: the silence window for a peer that has not finished one |
| `HeartbeatInterval` | 5 s | How long a link stays silent before one probe goes out |
| `HeartbeatTimeout` | 15 s | How long an unanswered probe waits before the peer is declared dead |
| `MaxFramesPerTick` | 64 | The ceiling on frames handled in one tick, so one loud peer cannot starve the loop |

A probe is sent only after silence, never on a timer: a link carrying traffic
produces no heartbeat frames at all. And nobody is cut off without being probed
first, so the worst case for noticing a dead peer is 5 + 15 = 20 seconds.

## Payload lifetime

`CycloneEvent.Payload` points into a buffer this connection owns and reuses. It
is valid until the **next tick on the same session**; after that the bytes may be
anything. Keep it longer and you must copy:

```csharp
byte[] mine = raised.CopyPayload();
```

The implementation guide (§6.2) allows either this or handing out an owned copy,
and asks that whichever one is chosen be stated plainly. This is the one chosen,
so a message costs no allocation on the receive path.

## Writing another transport

The four methods on `ITransport` are the whole contract, and they answer with
exactly six signals:

| Signal | Meaning |
|---|---|
| `Ok` | Done |
| `WouldBlock` | Not right now; ask again next tick |
| `Closed` | The peer hung up cleanly |
| `Error` | The link broke |
| `TooLarge` | This frame is past my ceiling - never retried, and the session survives |
| `NeedCapacity` | A packet arrived that does not fit; here is the size I need. The packet is kept |

Declare `TransportKind.Stream` and the runtime inserts its own reassembly layer
above you; declare `TransportKind.Message` and you must hand up exactly one whole
packet per `Receive`, never a fragment.

Nothing else is yours. Not framing, not ordering, not retrying a blocked send, not
measuring time, not reconnecting. And no method may block, sleep, spawn a thread,
or call back into the runtime.

`TcpTransport` and `UdpTransport` are roughly a hundred lines each; a new one
should be about that. If you find yourself needing to change the runtime to make
a transport work, something is in the wrong layer.

## Deliberately not here

- **No codec.** `Writer`/`Reader` for RFC-0002 is `cyclonec`'s generated output.
  A second copy in this repository would be a second implementation of the byte
  format in the same language, and RFC-0001 §6.1 is explicit that the two would
  drift silently - both sides decode fine, and the bytes stop matching.
- **No WebSocket, TLS or QUIC**, and no extension point pretending to leave room
  for them. A transport lives in its own library and implements `ITransport`
  without this one changing.
- **No background threads, no `async`.** Every socket is non-blocking and your
  `Tick` drives everything, which is invariant B2 of the implementation guide:
  no layer is allowed to block.
- **No reconnect, no reordering, no retransmission.** Cyclone does not do these,
  and a transport that quietly did them would leave the two ends disagreeing
  about whether the session is alive.

## Tests

`dotnet run --project tests/Cyclone.Net.Tests` runs 69 checks with no test
framework and no package restore. They follow the checklist in the implementation
guide §11:

- **wire format** - byte-exact frames, a byte stream fed one byte at a time,
  frames back to back, ceilings at 16 MiB and 1 MiB, and the deliberate asymmetry
  where a bad byte is fatal on a stream but costs only one packet on a datagram
- **handshake** - all four branches of the fingerprint gate, the query round in
  both directions, the two cases the guide flags as most often missed (a field
  appended by the client, a field dropped by the server - both must be accepted),
  malformed hellos, an enormous declared message count that must not overflow
- **heartbeat** - traffic suppressing probes, exactly one probe per silence,
  any frame clearing it, and a full expiry cycle proven without real waiting
- **core loop** - a blocked link parking one frame, congestion refused rather
  than queued, `NeedCapacity` not losing the packet, `TooLarge` not killing the
  session, the tick budget, and exactly one end event per session
- **end to end** - two peers over both link kinds, including a byte stream
  delivered one byte at a time
- **real sockets** - TCP and UDP on loopback, two UDP peers kept apart
